### 为什么没感觉到断网

`term` 与 `auth` 是**背靠背**执行的，中间只隔两次 HTTP 往返（每次几十毫秒）——
**离线窗口不到一秒**，TCP 重传直接盖过去了，所以浏览器和远程会话都没掉。
服务端 `logout-delay` 是 10 秒，也没触发。

### 这次跑出来一个真 bug（已修）

日志里有一行 `SyntaxError: unterminated string literal`。原因是我把「刷新网卡身份」
写成了 `.bat` 里的一行式 Python 命令，而 **cmd 会把 `%s mac=%` 当成变量名展开成空串**：

```

print('  ip=s gw= (c['wlanuserip'],...))  ← cmd 处理后 Python 实际收到的
```

后果：这个**安全步骤静默失效**（失败但脚本继续跑）——正是本工程最该防的
「不报错但没生效」。已把它挪进独立的 `refresh_identity.py`，并加了 `if errorlevel` 检查。

## 二·十、门户地址自动发现（2026-10-10）

### 结论：门户地址本来就"送上门"，是湖南适配把它改成了手填

未认证时，接入设备（BAS）会把明文 HTTP 劫持成 302，而那个 `Location` 里直接写着
门户地址、客户端 IP 和 `mscgip`。实测日志（`run.log`，2026-10-10 12:16）：

```
24: GET 地址: http://connect.rom.miui.com/generate_204
26: 临时移动, 重定向, 响应码: 302
27: 重定向至: http://175.12.104.1:10001/index.cgi?wlanuserip=100.67.199.113
             &mscgip=218.75.255.245&wlanusermac=AA-BB-CC-DD-EE-FF
30: 请求成功, 响应码: 200        ← 未认证时门户页确实是 200
37: 需要认证
```

五次真实掉线（21:50 / 22:04 / 22:14 / 22:36 / 22:45）内容完全一致。

**广东分支本来就是靠它工作的** —— `discover_guangdong()` 读的就是 `last_location`。
湖南适配时改成读配置，于是门户地址变成必须手填、换个接入设备就失效。

| 需要的东西 | 能否本地推导 | 302 里有吗 |
|---|---|---|
| 门户 `host:port` | ❌ | ✅ |
| 查询串 `mscgip` | ❌ | ✅ |
| 查询串 `wlanuserip` | ✅ 网卡 | ✅ 且是接入设备视角（更权威） |
| 查询串 `wlanusermac` | ✅ 网卡 | ⚠️ 带横线，需转换 |
| 报文 `<gwip>` | ✅ 默认网关 | ❌ |

注意 `<gwip>`（`100.67.192.1`）和 `mscgip`（`218.75.255.245`）**是两个不同的值**，
报文里各用各的 —— 302 给的恰好是推不出来的那一个。

### 三个"看起来可行、实际不行"的方案

1. **扫本地网段** —— 无效。本机 `100.67.199.113`、网关 `100.67.192.1`，而门户
   `175.12.104.1` 与 `mscgip` `218.75.255.245` **都在公网段**。
2. **DHCP option 252 / DNS** —— DNS 是 `222.246.129.81` / `59.51.78.211`（正常公网 DNS），
   不是门户；DHCP 252 要抓包才能读，且比现成的注入路径更脆弱。
3. **解析门户网页**（广东那套 `campus.js` 注释块）—— 湖南**走不通**。实测：

   | 请求 | 未认证时 | 已认证时 |
   |---|---|---|
   | `175.12.104.1:10001/index.cgi?<query>` | **200**（登录页） | **302 → `175.12.104.3:10003`** |
   | `175.12.104.3:10003/` | — | **412** + JS 挑战 |
   | `175.12.104.3:10003/index.cgi` | — | **403** |

   即 `175.12.104.1:10001` 是 **API 门户**，`175.12.104.3:10003` 是被动态防护挡着的
   **网页门户**（特征：随机响应头 `vvygpb7q`、随机 Cookie 名、`$_ts` JS 挑战、412 Precondition Failed）。
   跟着重定向走会拿到一个 `.cgi` 全 403 的地址。

### 最要紧的坑：要快照，不能沿用 `last_location`

`get_last_location()` 里的 `while (http_code == HTTP_FOUND) { 重发 last_location }`
循环会**不断覆盖** `last_location`，而 `discover_guangdong()` 读的正是它。
今天湖南**碰巧**没事（未认证时门户页回 200，循环不跑），但那是"碰巧对"。

所以实现上把**判定"需要认证"那一刻**的 Location 快照进 `prog_status_t.portal_hint`
（`CheckNetwork.c` 的 `remember_portal_hint()`）；`discover_hunan()` 优先用它，
快照缺失才退回 `last_location`，再退回配置 —— **三级回退，零回归**。

> 顺带记一笔：`portal_hint` 必须放在 `prog_status_t` 而不是 `auth_cfg_t` ——

## 二·十一、主动断开连接（2026-10-10）

### 语义

「断开连接」= **登出（服务端真的下线）+ 停止自动重连**，直到用户点「连接」。
不是"停一下" —— 断开期间认证线程不再被拉起，**没有任何网络流量**。

### 为什么不能只置 `is_need_reauth`

`clean()` 会 `memset` 整个 `runtime_status`，随后线程守护看到 `is_running == false`
就把线程重新拉起来 → 下一轮 `check_network_status` 看到"需要认证" → 立刻重新认证。
用户看到的"断开"就只是一次瞬断。

所以要一个**跨 `clean()` 存活**的标志：`runtime_status_t.is_manual_offline`，
在 `clean()` 里像 `is_time_disabled` 那样显式保存 / 恢复。

### 完整链路

```
Web 点「断开连接」
  → POST /api/disconnect                        (204)
  → 控制通道 "disconnect"（单进程模式直接置标志）
  → is_manual_offline = true; is_need_reauth = true
  → sleep_ms 被打断 → run() 返回 → 认证线程跳出主循环
  → clean() 里跑 term()          ← 真正的登出发生在这里
  → 线程守护看到 is_manual_offline, 跳过重启
  → 断开期间零流量

Web 点「连接」
  → POST /api/connect                           (204)
  → is_manual_offline = false
  → 线程守护下一轮重新创建认证线程 → 正常认证
```

两个角色都改了：单进程模式（`work()` 的线程守护）与独立认证进程（`work_auth()`，
它在 `wait_need_auth()` **之前**拦住 —— 断开后网络本就处于"需要认证"状态，不拦会立刻重连）。

### 一个附带用途：喊停重试

`/api/disconnect` **不要求当前已认证**。账号密码错时认证线程会按 1/5/10/20/30 分钟
退避一直重试，用户要能把它停下来 —— 那种状态下 `is_authed` 本来就是假。

### 验证方式（**没有真的断自己的网**）

新端点会真的把网断掉，所以测试时把控制端口指向一个**无人监听**的端口：

```
ESurfingClient.exe --role web --control-port 8891     (web_port 改成 8899, 隔离目录)
```

| 请求 | 结果 | 含义 |
|---|---|---|
| `GET  /api/status/auth` | 200 `{"status":false,"reachable":false,"offline":false}` | 新字段已生效 |
| `POST /api/disconnect` | **503** | 路由已接通，且因认证进程不可达**没有下发任何动作** |
| `POST /api/connect` | **503** | 同上 |
| `POST /api/no-such-route` | 404 | 与 503 明确区分，证明不是"什么都没接上" |

日志确认两条请求都走到 `WebApiPost.c` 的"认证进程不可达"拒绝分支；真实实例（8888）
与外网（204）全程未受影响。

> **真机上的断开行为尚未实测** —— 触发它会真的把网断掉，从而切断正在进行的会话。
> 复现方法：打开 <http://127.0.0.1:8888/>，点主卡上的「断开连接」，日志应依次出现
> `配置 1 登出` → `POST 地址: …/term.cgi` → `已断开连接, 等待「连接」指令`；
> 再点「连接」看是否恢复。

## 二·十二、配置方式重做：首次双击就能配好（2026-10-10）

### 问题：唯一能填账号的地方，在没配好时不存在

原来的流程**要求用户手工编辑 JSON**：

| 状态 | 旧行为 |
|---|---|
| 没有配置文件 | 生成模板 → 打印"请填写账号数据然后重启" → 退出（单进程模式下是**挂起**） |
| `enabled: false` | 打印"配置文件中禁用了程序启动" → 退出 |
| 账号为空 | "无可用配置" → 退出 |

而网页界面恰恰是**在配置加载成功之后**才启动的。也就是说，唯一能让用户填手机号、
密码、省份的地方，在他还没配好的时候根本不存在 —— 第一次双击等于什么都做不了。

顺带还有个既有缺陷：`enabled: false` 会让程序退出，于是**用户再也没法从网页把它
启用回来** —— 那个开关只在程序跑着的时候才点得到。

### 现在：把"配置是否可用"和"能不能跑起来"解耦

新增状态位 `g_cfg_ready`（= 已启用 **且** 账号密码齐全）：

- **为假** → 只启动网页界面，**不发起任何认证**，不发任何网络请求
- **为真** → 正常认证

配置文件缺失 / 为空 / JSON 坏掉 / 账号为空 / 被停用 —— 一律不再退出，改用内置
默认值继续跑，只是 `g_cfg_ready` 为假。用户在网页上点「保存并应用」，主循环重新
加载配置，就绪后自动进入认证流程。

```
双击
  → 生成/读取配置（无效也继续）
  → 启动网页界面              ← 关键：不再要求配置先成功
  → g_cfg_ready 为假 →【待配置】只等，不认证
  → 用户打开 http://127.0.0.1:8888 填手机号 / 密码 / 省份
  → 点「保存并应用」
  → 主循环重载配置 → g_cfg_ready 翻真 → 开始认证
```

运行中若用户在网页上停用或清空账号，认证线程会被停干净并回到【待配置】，
**网页界面始终在线** —— 那个开关现在真的能双向用了。

### 顺带修掉的两个真 bug

**① `/api/applyConfigs` 要求"当前已认证"。** 首次配置时认证线程本来就不存在，
于是这个接口回 403 —— 用户第一次填的账号**永远应用不进去**。已去掉这个门槛，
只要求"程序在运行"。

**② 端口被占用时程序会变成僵尸。** `start_web_server()` 只要线程创建成功就返回
`true`，而真正的 `bind` 是在线程里做的。端口被占用时主线程以为网页在跑，然后带着
一个**根本不存在的网页**进入待配置循环一直等 —— 实测 20 秒都不退出，用户看到
窗口在、网页打不开、程序也不干活。现在会等监听真正就绪，失败就 0.2 秒干净退出
并说明原因。

### 还挖出一个安全问题：网页界面可以被顶替

`minihttp.c` 原来用的是 `SO_REUSEADDR`。这个选项在两个平台上**语义相反**：

| | 语义 |
|---|---|
| Linux | 让 bind 不被 TIME_WAIT 挡住 —— 服务端该有的行为 |
| **Windows** | **允许别的进程再 bind 同一个端口，后绑的把新连接抢走** |

实测：隔离目录里的第二个实例明明该绑不上 8888，却绑上了。也就是说**本机任意一个
进程都能顶一个冒牌网页界面**，而那个界面会返回明文账号密码。已改为 Windows 用
`SO_EXCLUSIVEADDRUSE`（独占端口，第二个实例老实报 10048）。

### 默认模板也改了两处

```json
"enabled": true,          // 以前 false：填完账号还得再去开一次开关
"province": "hunan",      // 以前 guangdong，而 portal 却填着湖南门户 —— 自相矛盾
```

`province` 那处尤其要紧：用户看到 `guangdong` 会犹豫要不要改，漏改的话程序走广东
分支去找 `campus.js` 注释块，湖南门户没有那个东西，于是报"提取门户配置失败" ——
一个跟省份毫无关系的错误信息，极难定位。

### 验证（隔离目录，全程没碰真实客户端的网络）

| 步骤 | 结果 |
|---|---|
| 无配置启动 | 自动生成 `enabled:true` / `province:hunan`，网页起来，日志走通【待配置】 |
| 网页 API 填账号 → 保存 | `saveConfigs` **204** |
| → 应用 | `applyConfigs` **204**（旧版这里 **403**） |
| 应用之后 | `configured` 翻 **true**，日志"配置已就绪, 开始认证流程" |
| 端口被占用 | **0.2 秒**干净退出，退出码 1，提示"网页界面是本程序唯一的配置入口" |
| 离线自测 | 32 份官方抓包 密码层/报文层 仍 **32/32** |
| 真实客户端 | 全程未受影响（8888 正常、外网 204） |

> ⚠️ **首次双击时窗口仍然会关得很快**：配置生成、网页起来都发生在启动的头几秒，
> 之后程序就安静在后台跑了。找不到界面的话直接开 <http://127.0.0.1:8888/>。

## 二·十三、网页界面如实显示"实际使用的门户"（2026-10-10）

### 问题：界面把**回退值**说成了"程序在用的值"

二·十做完自动发现之后，用户在设置页看到的是「门户地址 `175.12.104.1`」「端口
`10001`」，很自然地认为那就是程序在连的地址。而实际上那只是**回退值** ——
未认证时程序用的是接入设备在 302 里下发的地址，两者可以不同。

下拉里那句「湖南（固定门户与端点）」更是直接把机制说反了：端点（一组 `.cgi` 名）
确实是固定的，门户地址却是发现优先的。

### 三个值必须分清

| | 存哪 | 谁写 | 用途 |
|---|---|---|---|
| `login_cfg.portal` / `portal_port` | `ESurfingClient.json` | 用户（网页表单） | **回退值**，设备不下发时才用 |
| `portal_hint` | 内存 | `CheckNetwork.c` 的 302 快照 | 发现过程的中间产物 |
| `runtime_portal` / `portal_source` | 内存 | `DialerAuth.c` 选定后写 | **只读快照**，只给界面显示 |

### 关键决定：**不**把发现值写回配置

本想直接把发现到的地址写进 `login_cfg.portal`（省一组字段），但这样会踩一个坑：

`/api/getConfigs` 回给网页的正是 `login_cfg.portal`，而网页保存走 `/api/saveConfigs`
是**原样写盘**（`Config.c` 的 `write_cfg_json`）。一旦被运行时值污染，用户点一次
「保存」就会把"接入设备当时下发的地址"**固化成配置文件里的死值** —— 回退机制当场
失效，下次接入设备一换连退路都没有。

所以运行时值必须另开一组只读字段。这也解释了二·十二里那条注释的意思：
`province` / `portal` / `mscgip` 之所以必须回给前端，正是因为保存是原样写。

### 改了哪些

| 文件 | 改动 |
|---|---|
| `include/states/States.h` | `prog_status_t` 新增 `runtime_portal` / `runtime_portal_port` / `portal_source` |
| `src/clients/dialer/DialerAuth.c` | `discover_hunan()` 选定门户后写入快照，`from_device` 决定来源 |
| `src/clients/net/CheckNetwork.c` | `auth_probe_url()` 探活优先用下发值，没有才回退配置 |
| `src/webserver/WebApiGet.c` | `/api/status/sys` 增加 `portal_live` / `portal_live_port` / `portal_source` |
| `portal/index.html` + `app.js` + `app.css` | 只读行「当前实际使用」、「关于」页两行、措辞修正 |

`portal_source` 三种取值：`"dhcp"`（设备下发，优先）/ `"config"`（设备未下发，
回退配置）/ `""`（还没判定过）。

### 已认证时这个量**不存在**，不能假装它存在

认证成功后探测返回 204，不再有 302，`remember_portal_hint()` 根本不会被调用。
所以此时界面显示的是"上一次认证采用"的地址，并在文案里**明确标注**：

```
接入设备下发，上次认证时采用
```

这一条是实测出来的，不是推测：隔离实例跑起来时本机正处于已认证状态，
`/api/status/sys` 一直返回 `portal_live: ""`、`portal_source: ""`，日志里
`need_auth` 一次都没出现 —— 正是"已在线所以没有 302"的真实表现。

### 验证

| 项 | 结果 |
|---|---|
| 编译（gcc 14.2.0 + Ninja，隔离目录） | 零警告零错误 |
| 离线自测：门户 URL 解析 | 19/19 + 查询参数 8/8 |
| 离线自测：32 份官方抓包 | 密码层 32/32、报文层 32/32 |

### 尚未验证的部分（要说清楚）

网络当前**处于已认证状态**，业务层不产生 302，因此 `portal_live` 在本机无法自然
填充 —— 实测到的是"尚未判定"这一支（`""`）。

### 顺带修正的认知

二·十说"换接入设备不再失效"讲得过于乐观。探活（`auth_probe_url`）发生在 302
**之前**，所以进程启动后第一次认证尝试仍然只能用配置里的门户去探活；探不通会被
判成 `CONNECT_ERROR`，程序认为"网络有问题"，可能根本不发起认证 —— 那时连发现的
机会都没有。

本次只把探活的**取值来源**换成"优先用上次下发值"（进程内第二次及以后的认证周期
因此受益），**没有**改"探活失败即拦截认证"这个判定本身。要根治得把探活失败降级
为"照常尝试认证"，那是主循环的行为改动，尚未做。

## 三、两个真实的坑（都已踩过并修好）
### 坑 1：湖南的补零规则与广东不同

广东版 `aes_double_cbc_android.c` 是**纯补零**：

```
total = ceil(L / 16) * 16
```

湖南官方客户端是**先补一个 NUL 结束符，再补零**：

```
total = ceil((L + 1) / 16) * 16
```

**只有在明文长度恰好是 16 的整数倍时两者才分歧** —— 而 `keep.cgi` 的明文正好是 **384 字节 = 16 × 24**：

| | 明文 L | 补零后 | 线上 body |
|---|---:|---:|---:|
| 官方（湖南） | 384 | 400 | **864 hex** |
| 广东规则 | 384 | 384 | 832 hex ← **少 16 字节** |

也就是说，**直接复用广东那一档，每次心跳都会短一整块**。32 份样本里只有 keep.cgi 命中这个分歧点，其余 4 个端点两种规则结果相同 —— 所以只测一个端点根本发现不了。

### 坑 2：`+1` 只作用于明文层，不能作用于中间层

第一版我把 `+1` 规则套在**两层**上，结果每个样本都多出 16 字节（672→704、576→608…）。

原因：第二层的输入是 `IV || C1`，**本来就是 16 的整数倍**，不能再补。Python 参考实现也是这个语义：

```python
inner = IV + AES(K1, IV).encrypt(_pad(plain))   # 这里 _pad 加 NUL
return IV + AES(K2, IV).encrypt(inner)          # 这里**没有** _pad
```

修法：给层函数加一个 `nul_pad` 参数，明文层传 1，中间层传 0。

## 三、湖南报文的精确格式（照官方抓包写死）

```
<?xml version="1.0" encoding="utf-8"?><request>\n
<k1>v1</k1>\n
...
<kn>vn</kn>\n
</request>          ← 收尾**没有**换行
```

五个端点的字段顺序（**不要重排**）：

| 端点 | 字段（按序） | 明文长度 |
|---|---|---:|
| `ticket.cgi` | ostag, local-time, gwip, mac, ipv6, ipv4, client-id, user-agent, host-name | 361 |
| `auth.cgi` | local-time, ticket, passwd, userid, client-id, user-agent | 299 |
| `state.cgi` | local-time, ticket, client-id, user-agent | 246 |
| `keep.cgi` | local-time, excheck-args, mac, ipv6, ipv4, ticket, client-id, user-agent | 384 |
| `term.cgi` | reason, local-time, ticket, client-id, user-agent | 265 |

**几个取值上的坑：**

- `ostag` = `Windows 11(26300),64 bit ` —— **结尾有一个空格**，不要 strip。
- `local-time` **不是固定占位符**。官方抓包里出现过 `00000000j/k/l/m`、`000000013`、`000000014`，共 9 字符。Python 版写死 `00000000l`/`00000000k` 也能被接受，但生成规则仍未破解。
- `mac` = **真实网卡 MAC**，格式 `AA-BB-CC-DD-EE-FF`（大写、短横线分隔）。
- `ipv4` / `gwip` = **真实 IP 与真实网关**（`100.67.199.113` / `100.67.192.1`）。
- `host-name` = 主机名大写（`TEST-PC`）。
- `excheck-args` = `<hello>57854</hello><conn>56487</conn>`，两份样本间**相同**；Python 版用 `<hello>1</hello><conn>1</conn>` 也能过。
- `user-agent` = `CCTP/WinSVR3/1052`（广东各档用的是 `WinSVR5/1068` 等，**不同**）。

> ⚠️ **注意**：广东版 `PlatformUtils.c` 的 `create_xml_payload()` **不能**用来发湖南报文 ——
> 它没有 `excheck-args`、没有 `reason`、没有 `state.cgi`，`term` 用的是和心跳同一个模板。
> 湖南用新写的 `hunan_build_xml_for()`。

## 四、怎么编译

> ### ⚠️ 必读：`mingw\bin` 必须加进 `PATH`
>
> gcc 会 spawn `cc1.exe`，而 `cc1.exe` 需要同目录的 `libwinpthread-1.dll` /
> `libgcc_s_seh-1.dll`。**只用绝对路径调用 gcc 是不够的** ——

> `0xC0000135` = STATUS_DLL_NOT_FOUND）。这个坑排查了很久。

```bat
set "PATH=C:\temp\esurfing_build\mingw\bin;%PATH%"
```

| 脚本 | 作用 |

## 六、下一步（按顺序）

**步骤 6：联网实测 `auth.cgi` + `term.cgi`**（当前卡点）

这两个是**唯一会真正改变连接状态**的端点：`term.cgi` 注销 = 断网，`auth.cgi` 重新认证 = 恢复。
一旦断网，公网出口就没了，**远程会话（也就是我）会直接失联**，所以必须：
- 挑一个可以接受失联的窗口；
- 而且要有**不依赖我**的兜底恢复手段。

建议做法（安全序）：
1. 先 `python run.py logout` 注销（或用 `hunan_live` 的 term 版本）
2. 立刻用 **C 版** 走一遍完整 `ticket → auth → state → keep`
3. 若 C 版失败 → 立刻跑 `启动拨号.bat`（Python 版）把网恢复
4. 全程不需要我在线

> ⚠️ 注意：`auth.cgi` 在**已在线**时打，可能被服务端当成「重复认证」拒绝（`Error-Code=102`），
> 所以这一步的真实性必须建立在「先注销」之上，不能省。

**步骤 7：静态算法通道**

`DialerSession.c` 的 `init_session()` **无条件**把 `algo_id` POST 到 `ticket_url` 并当 ZSM 解包。
湖南的 `ticket.cgi` 返回的是加密 XML 票据（实测 352 字节响应），不是 ZSM，
而且此刻 `algo_id` 还是全 0 UUID，`init_cipher()` 必然返回 NULL。

需要加一条分支：**跳过 ZSM 拉取 → 直接把 algo_id 设成 `FAB1DCDE-…` → 用本地密钥表初始化 cipher**。

**步骤 8：门户/端点**

`CheckNetwork.c:7-8` 的 `AUTH_URL`/`AUTH_BAK_URL` 是广东的 `14.146.227.141:7001`。
湖南用 `175.12.104.1:10001`。
**好消息**：实测发现 `state.cgi` 的响应里带 `keep-url`/`term-url`，
所以端点**可以运行时发现**，不必写死；只有 `ticket.cgi`/`auth.cgi` 需要先有门户地址。
`mscgip` 仍需从 302 跳转里挖（或沿用 config.json 里的值）。

**步骤 9：真实网卡身份**

广东版 `reset_mac_addr()` 是**随机生成** MAC 的，也没有网关查询。
湖南官方客户端发的是真实 MAC / 真实 IP / 真实网关（实测 `TEST-PC` / `AA-BB-CC-DD-EE-FF` / `100.67.199.113` / `100.67.192.1`），
所以必须接上真实的网卡枚举。`src/utils/NetAdapters.c` 已有雏形，需要确认它给的是不是真实值。
